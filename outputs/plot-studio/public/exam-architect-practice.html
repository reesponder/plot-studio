Build the intake endpoint.

Task instructions

Expose POST /api/workshop-requests to site visitors. Accept a valid email and an integer seat count from 1 through 6. Convert numeric form text, such as “2”, to a number before validating. Reject missing or invalid inputs without inserting a row. Create valid rows with status new and return HTTP 201 with {id, status}. Leave email out of the response.

How I solve it

  1. Create the route and verify the table

    I make Email, Seats and Status required in Workshop requests. I use the Email, Integer and Text types respectively. I copy their actual field IDs from Data and leave visitor access to the table off. In Backend I add POST /api/workshop-requests with Site visitors access.

  2. Validate on the server

    I bind request.body.email to Require email address. I check request.body.seats with Require comparison set to exists, then use To number. I feed the converted value to Require integer and Require number range, with bounds 1 and 6. I send validation errors to HTTP 400 before the create action can run.

  3. Write one row and choose the public fields

    In Create record I map the actual table field IDs to the validated email, integer seats and literal status new. In the 201 response I use Object fields to select just id and status from the create output. For a create node named create-request, the ID reference is steps.create-request.value.id. I handle write errors separately from validation errors.

  4. Verify the response and the write

    I check the response and trace in Request test. In a rehearsal database, I compare the rows before and after each request to confirm that rejected requests leave the table unchanged.

How I check it

sample@example.com and seats "2"
HTTP 201 with an ID and status new. There is one new row with integer seats 2. The response has no email field.
Seats 1 and 6
Both boundary values produce HTTP 201 and their numeric values are stored.
Seats 0, 7, 2.5, or missing
Client error. The request never reaches Create record and the row count is unchanged. An invalid email produces the same no-write result.

Protect the lookup endpoint.

Task instructions

Build GET /api/workshop-requests/:id with API key required and the PLOT_API_KEY secret alias. A valid key and existing ID return HTTP 200 with {id, status, seats}. Missing or invalid keys return 401 and an unknown row returns 404.

How I solve it

  1. Configure access on the endpoint

    I set the method to GET and the path to /api/workshop-requests/:id. Under Access I choose API key required and set the secret alias to PLOT_API_KEY. I make the test key available only to the test server and the request client.

  2. Read the requested row

    I choose Workshop requests in Read record and map Record ID from request.params.id. I leave On error set to Stop with error. The node already returns 404 for an unknown ID and preserves the different status for a storage error.

  3. Build an allowlisted response

    I use Object fields in the 200 JSON response to return exactly id, status and seats. If I call the lookup step read-request, I bind the ID to steps.read-request.value.id and use the actual Status and Seats field IDs on that same value. Selecting those three fields also keeps future table columns out of the response.

  4. Test authentication on the running service

    I publish to an isolated rehearsal site with a temporary key. On that same site I create a synthetic row through the intake route and copy its generated ID. I call the lookup route with Authorization: Bearer <test-key>, then repeat with a wrong key and with the header removed. Finally I keep the valid key and change the ID to one I know does not exist.

    I use Request test for the workflow trace. It bypasses the endpoint’s API-key check and uses a fresh copy of the draft data, so I use the running service for proof of authentication and for tests that span two requests.

How I check it

Valid Bearer key and existing ID
HTTP 200 with exactly id, status and seats. The row’s email never appears.
Missing or wrong Bearer key
HTTP 401. No record details are returned.
Valid key and unknown ID
HTTP 404 from the configured lookup route.

Verify the partner callback.

Task instructions

Build POST /api/workshop-events. Verify HMAC SHA-256 against request.raw and request.headers.x-workshop-signature using secret alias PLOT_SECRET_WEBHOOK. The signature can be lowercase hex, with or without a sha256= prefix. An authorised event can update an existing row to approved or rejected and returns HTTP 200 with {id, status}. Reject absent or invalid signatures and invalid statuses without writing. Return 404 for an unknown record.

How I solve it

  1. Verify the raw request before any database action

    I add POST /api/workshop-events with Site visitors access. The first action is Verify HMAC signature. I bind Signed text to request.raw, Signature to request.headers.x-workshop-signature and Server key alias to PLOT_SECRET_WEBHOOK. I connect On error to Error response with status 401 and a generic message. The only wire leading to the database goes through On success.

  2. Validate the action from the verified sender

    On the verifier’s success output I validate request.body.id and pass request.body.status to Require allowed value with ["approved","rejected"]. I use Update record with that ID and bind just the Status field. Its default error path returns 404 for an unknown ID. On success I return HTTP 200 with the same ID and the updated status.

  3. Make a disposable fixture

    I prepare a raw JSON body with a sample record’s ID and status approved. I compute the HMAC-SHA256 hex digest for those exact bytes with a test-only secret. I set the corresponding alias in Request test, use a row already saved in draft Data and compare results with and without the sha256= prefix. Even a change to whitespace changes the bytes the verifier sees.

  4. Repeat the callback against persistent data

    In a single isolated rehearsal release I set the server secret, create a sample row, then send the same signed event twice. I read the row after each delivery and compare its ID, status and the total row count. Then I keep the signature but edit the body, and try again with the signature header missing. I also sign a body with an invalid status to confirm that a valid signature doesn’t authorise an invalid change.

How I check it

Correct signature, either prefix format
HTTP 200 with the original record ID and status approved. Replaying the same event leaves one row with that same state.
Missing signature or altered body
HTTP 401. The stored status and row count stay as they were.
Correct signature with invalid status or unknown ID
Invalid status returns a client error and writes nothing. An unknown ID returns HTTP 404.

Connect the browser form.

Task instructions

Use required email and number fields with names email and seats. Prevent the native submission. Wire Form submission to Call backend route for POST /api/workshop-requests, with the Fields output connected to the request body. Route success and error to separate Set text nodes with distinct messages visible to the visitor.

How I solve it

  1. Use the same names as the request contract

    I add Email and Seats to the workshop form, with field names email and seats, types Email and Number, and Required enabled. I place a status paragraph below the submit button so users can see the result on a phone.

  2. Bind execution and submitted values

    In Logic I point Form submission at this form and prevent the native submission. I add Call backend route, select POST and enter /api/workshop-requests. I connect the event’s execution port to the action and its typed Fields output to the request body.

  3. Show both server outcomes

    I connect Success and Error to separate Set text nodes targeting the status paragraph. I use “Your request was received.” for Success and “We couldn’t submit your request. Check the details and try again.” for Error.

  4. Run the graph through the browser

    I test on an isolated rehearsal site where the backend route is available. I submit a valid sample email with two seats, then try seven seats. If the browser’s own maximum blocks that second input, I exercise the server rejection in a disposable copy without the field maximum while keeping the backend rules intact.

How I check it

Sample email and seats 2
The form stays on the page, shows the success message and results in a single new row.
Email missing
The required-field check blocks submission. No request is sent and there is no new row.
Seats 7 submitted to the backend
The server rejects the request. The Blueprint follows Error, changes the visible text, and creates no row.
